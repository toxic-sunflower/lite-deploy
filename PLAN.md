## How to start any session

1. Read `VISION.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `PLAN.md`, `SPEC-v0.md`.
2. Take the first unfinished session from the list below, unless the owner names another.
3. Work in short steps, one action at a time, every command with an explanation, no allegories. Do not use "I won't"; "I can't, because …" is acceptable. Do not explain what the owner knows (for example, what `sudo` is).
4. Do not ask for secrets in the chat and do not print them.
5. Any action on a real server only with the owner's explicit permission. Do not touch the production server unless told otherwise. Tests go to separate servers and the owner's WSL.
6. Do not revisit decisions without a reason: they are in `DECISIONS.md`. If something has to change, propose the change and record a new decision.
7. At the end: update the files, commit, push, write a summary in three to five lines.

Checks before pushing: `go vet ./...`, `go test -race ./...`, `golangci-lint run ./...`.

A template of the first message for a new session:

> Read VISION.md, ARCHITECTURE.md, DECISIONS.md, PLAN.md and SPEC-v0.md. We are doing session S<number>. Let's go in short steps.

## Notes on the environment

- The cloud environment has Go 1.24 and systemd and no Podman. The logic (config parsing, plan building, input validation, schema generation) can be written and tested there. Applying with rootless containers has to be checked on a separate server or in the owner's WSL.
- The `WebFetch` tool does not see domains allowed in the network settings. `curl` works through a proxy. To read documentation, domains must be allowed in the environment settings (Network access).
- A test server is needed no later than session S4.
- Go modules install if the environment's Allowed domains include `proxy.golang.org` and `sum.golang.org` (with "Allow package managers" ticked). Inside a session `NO_PROXY` must be reset: `export NO_PROXY=localhost no_proxy=localhost`, otherwise `go` goes directly and finds no DNS. Do not disable checksum verification (`GOSUMDB`). Dependencies: `filippo.io/age`, `golang.org/x/term`. The schemas are generated by our own small reflector in `internal/schema` (no external libraries).
- `golangci-lint` is installed (v2.5), configured in `.golangci.yml`.
- After a PR is merged, the development branch is restarted from `main` (the same name).

## The goal: the product (v1)

The product is v1 (D-47): an agent daemon with an on-request executor (modes A and B), a UI, an MCP for AI, secrets write-only with confirmation by a signature, installation on an empty server with one command. The first version (v0, S3–S5) is a step on the way: to check the core on a live project before building a daemon on it. v0 is not released separately.

The project priority: AI (MCP) and the UI.

## TODO

- **T1 (done 2026-11-20). Change your SSH key without losing access.** `lite ssh-key list|add|remove` works on your own `~/.ssh/authorized_keys` (no root). A key is replaced in two steps: `add` the new one (the old one keeps working), log in with it, then `remove` the old one; removing your last key is refused.
- **T2 (done 2026-11-20). Hints about what to do next.** After every setup step (`lite init`, `lite security …`, `lite backup …`, `lite project create`, `lite deploy`) and in `liteup`, print the next step to take, with the exact command, for example after `init`: "check key login in a second window, then `lite verify`". `lite verify` must say what to do next too, not only `lite init`: after its findings it prints the ordered next steps with exact commands (for example "run `lite security fail2ban`", then "`lite backup setup …`"), and "nothing left to do" when all is green.

- **T3 (done 2026-11-20). Updates: notice and install.** `lite verify` and the UI say when a newer `lite` release exists (the data of `liteup status`) and when updates of components (Caddy, PostgreSQL, podman, Redis) or security updates are waiting. The UI has an "Update" button: `liteup update` runs through the agent and executor without sudo; the release signature is checked as now, and if the new version does not start, the previous one is restored. Tested on a clean virtual machine before a release (T9).
- **T4 (done 2026-11-20). Protection fully on by default.** `lite init` does everything itself: fail2ban, automatic updates, kernel parameters, and SSH by key only for everyone (root by key only), so `lite verify` has no security errors right after `init`. `--no-security` skips it. `init` already requires a key for the new user, so the lock-out risk is the same as today; it still tells the person to check a second login. `allow-users` stays optional. Caddy, podman, PostgreSQL and Redis stay opt-in.
- **T5 (done 2026-11-20). Hints must not say `sudo`.** The `fix:` lines of `lite verify` print `sudo lite security …`, but daily commands run without sudo (R-16). Print the command as it is run: `lite security …`.

- **T6 (done in the interface, 2026-11-20). Built for non-professionals, UI first.** The whole path is in the interface in plain words: protection, projects, publishing, databases, backups with a key made on the person's computer, off-site copies, updates, MCP. Terminal commands stay for those who like them. What is left is the live check (`TESTING.md`).

- **T7 (done 2026-11-20). No wrappers over system tools.** The commands `lite security fail2ban|updates|sysctl` were removed: those protections are always on while the `security` plugin is installed (`init` installs it). `lite security ssh` stays, as do `enable`, `allow-users`, `banned`, `unban` and `logins`.
- **T8 (done 2026-11-20). The whole path is: install `lite` on the server, `lite init`, hand over the key, then only the UI, with a separate small UI client.** After `init` the server is already protected (T4) and nothing else is needed in a terminal. On the person's computer there is no full `lite`: a separate, small UI-only program (one file per system, for example `lite-ui`, built from the same code without the agent and executor) is downloaded from the releases and started with a double click; no `liteup`, no PATH, no terminal. It reaches the server over SSH with the person's key and opens the page in the browser. The server opens nothing to the internet for it. The full `lite` stays on the server and for people who prefer a terminal.
- **T9 (replaced by `TESTING.md`, 2026-11-20). Checking a release.** There is no spare machine, so the release candidate is walked through on the owner's real server and project by the scenarios in `TESTING.md` (and the clean-VM steps in `RELEASING.md` stay for anyone who has a spare machine).

- **T10 (done 2026-11-20). `init` checks the key login itself.** The person should never have to "keep a second session open". Before `init` closes password login, it waits until the person has really logged in with the new key (it watches the SSH login journal for a successful key login of that user) and only then applies the SSH protection; until then password login stays on. If the login does not appear within a few minutes, `init` leaves password login on and says so.

- **T11 (done 2026-11-20). One connection per server.** `lite-ui` keeps one ssh connection to a server and sends every request through it (`lite-deploy call-stream` on the server), on every system including Windows. An older server without the command is served with one ssh per request. After a failed login `lite-ui` stops trying for a minute.

- **T22. Dependencies of a project as a general idea (the core must not know PostgreSQL).** Today the project description has a fixed `database` field and the code that makes the database, the user and the password lives in the core (`internal/plan`), and `project.Requires` names `pg`. Redis cannot be a dependency (it can only be installed), and MySQL has no plugin. The target: a project lists what it needs (a database, a cache, a queue) as `needs`; each plugin (`pg`, `mysql`, `redis`) makes the resource (a database or a keyspace, a user, a password) and returns the connection settings; the core only passes them to the application. The form of a project is built from the installed plugins. Podman and Caddy may stay known to the core (they are the standard runtime and ingress). Order: a plugin interface for "provide a resource", move PostgreSQL behind it without changing the behavior, then Redis and MySQL. The address of a resource is not a fixed list of formats (url, npgsql, libpq): the application gets the **parts** as separate settings (host, port, name, user, password) and one ready `DATABASE_URL`; whoever needs another notation writes a **template** with placeholders (for example `Host={host};Username={user};Password={password};Database={db}`) and lite only substitutes the values. Today `connection_format` (a choice of three) is in the project description and the form; it becomes the optional template.
