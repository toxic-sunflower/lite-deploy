# План работы и сессий

Каждая сессия короткая и решает одну задачу. В конце сессия обновляет `DECISIONS.md` и этот файл, делает коммит и пуш в ветку. Pull request без просьбы владельца не создаётся.

## Карта документов

| Файл | О чём |
|---|---|
| `VISION.md` | Замысел, принципы, границы |
| `ARCHITECTURE.md` | Как устроено (схема, части, безопасность) |
| `DECISIONS.md` | Что решили, почему, статус |
| `PLAN.md` | Этот файл: очередь сессий |
| `COMPARISON-PLAN.md` | План сравнения с аналогами (выполнен частично) |
| `WALKTHROUGH.md`, `DEPLOY-PATTERN.md` | Ручной проход и схема деплоя, эталон поведения |
| `projects/fanvue-games/` | Реальный проект, эталон для сценариев |

## Как начинать любую сессию

1. Прочитать `VISION.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `PLAN.md`.
2. Взять первую невыполненную сессию из списка ниже, если владелец не назвал другую.
3. Работать короткими шагами, одно действие за раз, каждую команду с объяснением, без аллегорий. Не использовать «не буду», допустимо «не могу, потому что …».
4. Секреты не просить в чат и не печатать.
5. Любое действие на реальном сервере только с явного разрешения владельца. Реальный сервер (`187.7.72.122`) трогать нельзя, пока не сказано иначе: там работает FanVue Games.
6. В конце: обновить файлы, закоммитить, запушить, написать итог в три-пять строк.

Заготовка первого сообщения для новой сессии:

> Прочитай VISION.md, ARCHITECTURE.md, DECISIONS.md и PLAN.md. Делаем сессию S<номер>. Идём короткими шагами.

## Заметки об окружении

- В облачной среде есть Go 1.24 и systemd, нет Podman. Логику (разбор конфига, построение плана, проверку ввода) можно писать и тестировать здесь. Применение с rootless-контейнерами нужно проверять на отдельной виртуалке или одноразовом VPS с чистой Ubuntu 26.04.
- Инструмент `WebFetch` не видит домены, разрешённые в настройках сети. Работает `curl` через прокси. Чтобы читать документацию, нужно разрешить домены в настройках среды (Network access).
- Нужен тестовый сервер не позже сессии S5.

## Очередь сессий

### S1. Закрыть оставшиеся решения (короткая)
- Цель: принять решения, без которых нельзя начинать: название проекта, лицензия, цель проекта в одной странице, определение первой версии (что входит и что нет), какие действия считать опасными по умолчанию, краткая модель угроз.
- Результат: обновлённые `DECISIONS.md` и `VISION.md`; отдельный файл с моделью угроз при необходимости.
- Не делаем: код.

### S2. Спецификация v0
- Цель: описать формат проекта, формат плана, список действий исполнителя для `project create`, эскиз API, структуру репозитория.
- Вход: S1, `projects/fanvue-games/`, шаги 11–12 и 18 `WALKTHROUGH.md`.
- Результат: `SPEC-v0.md`.
- Не делаем: код.

### S3. Каркас репозитория и чистая логика
- Цель: Go-модуль, структура каталогов, линтер, CI, разбор описания проекта, проверка ввода, построение плана. Всё проверяется тестами здесь, без сервера.
- Результат: код и тесты; `go test -race` зелёный.
- Не делаем: применение плана.

### S4. Применение плана (режим А), команда `project create`
- Цель: плагины `base` (проверки), `postgres` (роль и база через unix-сокет), `caddy` (файлы сайта, проверка от пользователя `caddy`, reload), движок `podman` (пользователь, linger, юниты), применение плана одной командой.
- Вход: S3, готовые скрипты `01..04`, `verify.sh`.
- Результат: работающая команда на тестовом сервере.
- Не делаем: демон, UI, подтверждения.

### S5. Привратник, `deploy`, `rollback`, `status`
- Цель: перенести привратник и blue-green из `projects/fanvue-games/` в общий вид. Ограниченный ключ, проверка хэша, проверка `/health/ready`.
- Результат: выкатка тестового проекта с откатом.

### S6. Туннель Cloudflare
- Цель: плагин `tunnel-cloudflare` по правилам из `DEPLOY-PATTERN.md` (отдельный пользователь, токен 600, проверка старых DNS-записей, запасной план на случай сбоя).

### S7. Секреты и бэкап
- Цель: ссылки `secret://`, локальный бэкенд с записью без чтения, шифрованный экспорт и восстановление сервера одной командой.

### S8. Агент-демон, исполнитель и подтверждения (режим Б)
- Цель: служба на сокете, разделение агента и исполнителя, журнал, подтверждение подписью ключом.
- Нужно до этого: решение о протоколе и способе разделения процессов (из S2).

### S9. Локальный UI
- Цель: `ctl ui` на компьютере владельца, ходит по SSH к агентам.

### S10. MCP-клиент
- Цель: тонкий MCP-сервер над API агента; права и подтверждения остаются в агенте.

### S11. Установка с нуля, инструкция и скилл
- Цель: установка агента на пустую Ubuntu одной проверяемой командой; инструкция «что и зачем ставится» (пункт 1 из первоначального замысла) и скилл для ИИ-агента (пункт 2).
- Вход: `skill/server-setup`, `WALKTHROUGH.md`.
