# FanVue Games: сервер и деплой, очередь работ

Это знания об инфраструктуре проекта. Они **намеренно лежат вне репозитория приложения**: репозиторий не должен подсказывать, как устроен сервер. Папка `projects/<проект>/` задумана как образец для будущей системы развёртывания разных проектов (см. `../../VISION.md`).

Идём по шагам вручную, с объяснением каждой команды (владелец хочет понимать, что делает). Описание схемы: `README.md` рядом, решения: `decisions.md`, состояние: `STATUS.md`.

## Деплой на сервер

На компьютере владельца (WSL):
- [ ] 1. Создать пару ключей деплоя (ed25519, без пароля, подпись `github-actions-fanvue-games`). Закрытый ключ нужен только чтобы один раз вставить его в секрет GitHub, потом файл можно удалить.
- [ ] 2. Скопировать на сервер (в `/tmp`): привратник `bin/fanvue-ssh-gate`, скрипт `bin/fanvue-deploy`, юниты `quadlet/*.container`. Всё это ставится вручную (решение 2026-10-24).

На сервере (под `serafim`):
- [x] 3. Привратник положен в `/home/fanvue-games/bin/` (владелец `fanvue-games`, права 700). Сделано, но версию на сервере надо заменить новой (привратник стал проще: больше не принимает архив).
- [ ] 3б. Скрипт `fanvue-deploy` в `/home/fanvue-games/bin/` (права 700), юниты в `/home/fanvue-games/.config/containers/systemd/` (права 600, владелец `fanvue-games`, создавать каталоги от имени самого пользователя), затем `systemctl --user daemon-reload` от его имени. После этого `rm` временных файлов в `/tmp`.
- [ ] 4. Вписать открытый ключ в `authorized_keys` пользователя `fanvue-games` строкой `command="/home/fanvue-games/bin/fanvue-ssh-gate",restrict ssh-ed25519 ...` (файл `.ssh` с правами 700, `authorized_keys` 600). Не `ssh-copy-id`: он добавит ключ без ограничений.
- [ ] 5. Правило `sudoers`: пользователю `fanvue-games` только `/usr/bin/systemctl reload caddy` без пароля.
- [ ] 6. Файлы настроек в `/home/fanvue-games/.config/fanvue-games/` (права 600, владелец `fanvue-games`): `deploy.conf` (имена образов GHCR), `admin.env` (строка подключения, `Admin__Username`, `Admin__Password`), дополнить `app.env` секретами (`Auth__SessionSecret`, `Fanvue__ClientId`, `Fanvue__ClientSecret`, `Fanvue__RedirectUri`, `Fanvue__AppUuid`, `Fanvue__WebhookSecret`). Секреты вводит владелец сам, в чат не присылать.
- [ ] 7. Вход сервера в GHCR под `fanvue-games` токеном только на чтение пакетов (`machinectl shell fanvue-games@ ... podman login ghcr.io`).
- [ ] 8. Каталоги Caddy: `/etc/caddy/upstreams` (владелец `fanvue-games`, два начальных файла upstream: сервис и админка), `/var/log/caddy`.

На GitHub:
- [ ] 9. Окружение `production` (ветки `main` и `release`), секреты окружения `DEPLOY_SSH_KEY` (закрытый ключ), `DEPLOY_KNOWN_HOSTS` (отпечаток сервера, сверить вручную), `DEPLOY_HOST`, `DEPLOY_USER`; ветка `release`; защита ветки `main` (без прямых пушей, 2FA на аккаунте).
- [ ] 10. Переменная репозитория `DEPLOY_ENABLED=true`, когда всё готово.

## До боевого запуска (запуск на следующей неделе, 2026-10-24)

- [ ] Cloudflare и туннель `cloudflared` (решено: туннель, ручной запасной план). Шаги в `README.md`, «Разовая настройка», п. 6. Домен пока свой у владельца, потом перепривязать (имена в файлах Caddy и в туннеле).
- [ ] Первая выкатка, проверка blue-green и отката.
- [ ] Прогнать запасной план (`caddy/fanvue-games.fallback.caddy.disabled`, раздел «Если Cloudflare недоступен» в `README.md`): включить, проверить, вернуть.
- [ ] Проверить файлы Caddy настоящим Caddy (синтаксис, `http://имя:18080` с `bind 127.0.0.1`, чужое имя ничего не отдаёт, `X-Forwarded-For` из `CF-Connecting-IP`, лимиты тел запроса, переключение upstream после `reload`). Владелец делает это сам по командам из чата, скриптов в репозитории нет.
- [ ] Правило Cloudflare для `POST /api/webhooks/fanvue` (пропуск проверок ботов).
- [ ] Проверка изоляции после первой выкатки: из контейнера достать `localhost:2019` (API Caddy) и другие порты хоста; из-под `fanvue-games` попробовать подключиться к другим базам и к `postgres` (должно не пускать); просмотреть `pg_hba.conf` (`sudo grep -v '^#'`) на правила с `all`. `admin off` в Caddy ставить нельзя (ломает `systemctl reload caddy`), при необходимости переводить API на unix-сокет и проверять reload.
- [ ] Проверка, что секреты нигде не светятся (на сервере, только чтение): `/etc/environment`, `/etc/profile.d/`, `/etc/systemd/system.conf.d/` и `~/.bash_history` пользователя `serafim` на пароли и токены (`grep -i -E 'password|secret|token|PW='`); что `app.env`, `admin.env` и `deploy.conf` с правами 600 и владельцем `fanvue-games`.
- [ ] Защита `main` и окружения `production` (шаг 9) и 2FA на аккаунте GitHub: от них зависит, что вообще попадёт в образ. Рассмотреть обязательное одобрение деплоя в окружении.
- [ ] Консоль хостера как запасной вход: выяснить, есть ли, до отключения входа по паролю.
- [ ] Отключить вход по паролю в SSH (`PasswordAuthentication no` в `/etc/ssh/sshd_config.d/00-hardening.conf`) после проверки входа по ключу (вторая сессия!) и наличия консоли.
