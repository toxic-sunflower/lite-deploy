# FanVue Games: решения по серверу и деплою

Решения владельца с причинами. Приложение и продукт описаны в репозитории приложения (`docs/decisions.md`), здесь только инфраструктура.

## Сервер и общая схема (2026-10-23)

- **Сервер общий с другими проектами**, Ubuntu 26.04, Caddy и PostgreSQL 18 на хосте (PostgreSQL из архива Ubuntu, Caddy из официального репозитория), приложения в rootless podman под отдельным пользователем на проект (`fanvue-games`), службы через Quadlet.
- **Настройка сервера не хранится в репозитории приложения** (решение владельца, подтверждено 2026-10-24: репозиторий не должен подсказывать, как устроена инфраструктура). Всё серверное лежит здесь, в `projects/fanvue-games/`, как образец для будущей системы развёртывания разных проектов. В репозитории приложения остаются только `Dockerfile`-ы, workflows (их читает GitHub) и локальный `compose.local.yaml`.
- **Образы собирает GitHub Actions** (приватный GHCR, теги: полный хэш коммита и latest), сервер исходников не хранит. Деплой по SSH ограниченным ключом (принудительная команда: только `deploy <хэш>`, `rollback`, `status`), секреты в GitHub (окружение production, секреты окружения: ключ, отпечаток сервера, адрес сервера, имя пользователя).
- **Blue-green** (два слота на локальных портах, переключение через файл upstream в Caddy). **Автодеплой** при слиянии в `main`; **кнопка** Run workflow (только из `main`); отдельная **кнопка отката**. Всё идёт на одно боевое окружение под одним адресом (нужен один URL для Fanvue). Миграции БД обязаны быть обратно совместимы.
- **Админка тоже blue-green** (решение 2026-10-24, прежде перезапускалась без проверки, и сломанную версию откат не возвращал). Сервис и админка делят одно состояние и переключаются вместе одним коммитом; в админке для проверки добавлен `/health/ready` с версией. Порты: сервис 18081 и 18082, админка 18091 и 18092, сайты в Caddy на 127.0.0.1: сервис 18080, админка 18090.
- **База проекта через unix-сокет** (решение владельца): роль `fanvue_games`, пароль только на сервере (файл `app.env`, права 600). Подробности и команды: `README.md`, раздел «База данных».

## Файлы деплоя ставятся вручную (2026-10-24)

Привратник, `fanvue-deploy` и юниты Quadlet ставятся на сервер вручную, Actions шлёт по ограниченному ключу только команду `deploy <хэш>` (заменило первую схему, где пайплайн присылал архив со скриптом). Причина: присланный скрипт выполнялся бы на сервере от `fanvue-games`, то есть ключ деплоя мог выполнить любой код (и даже поменять `authorized_keys`). Теперь при компрометации GitHub можно лишь запустить деплой образа из GHCR. Недостаток: правки деплоя ставятся вручную; позже это автоматизирует отдельная система развёртывания (`../../VISION.md`). Права: привратник и скрипт 700, юниты 600.

## Cloudflare (решено 2026-10-24)

- **Туннель `cloudflared`**, а не прокси с сертификатом Origin CA. Сайты слушают только `127.0.0.1` (18080 и 18090), оба имени идут через туннель, Cloudflare Access на имени админки. Прямого входа по IP нет, поэтому Authenticated Origin Pulls и сертификат Origin CA не нужны. Сервер общий, порт 443 нужен другим проектам, поэтому закрыть его целиком нельзя, а туннель защищает именно этот проект.
- **Запасной план при сбое Cloudflare ручной:** `caddy/fanvue-games.fallback.caddy.disabled` (публичный сертификат Let's Encrypt, DNS без прокси). В обычное время выключен: включённый запасной вход возвращает обход Cloudflare. Автоматического запасного входа нет.
- Загрузка файлов через бесплатный Cloudflare до 100 МБ.
- Домен сайта: пока домен владельца, потом перепривязать (имена в Caddy и туннеле).

## Секреты

Пароль БД и секреты приложения только на сервере (файлы с правами 600). В GitHub только ключ деплоя, отпечаток, адрес и имя пользователя. Токены Cloudflare и GHCR вводит владелец в своей оболочке (`read -rs`), в чат и в репозиторий не попадают. В репозитории приложения настоящих секретов нет (проверено 2026-10-24).

## Изоляция проектов на общем сервере (2026-10-24)

- Каталог сокета Postgres монтируем в контейнер целиком: сокет один на весь сервер, границу задают роли, пароли и `pg_hba.conf` (подключение как чужая роль без пароля невозможно, остаётся подбор паролей, поэтому пароли длинные и случайные). Монтировать один файл сокета вредно (после перезапуска Postgres ссылка мёртвая).
- `admin off` в Caddy нельзя: `systemctl reload caddy` использует это API.
- Лимиты ресурсов в юнитах уже есть (`Memory=`, `PidsLimit=`).
- Защита секретов GitHub держится на ограничении окружения `production` веткой `main` и 2FA владельца (защита веток на бесплатном тарифе для приватного репозитория недоступна); ключ деплоя на сервере всё равно умеет только `deploy`, `rollback`, `status`. Полный чек-лист: `../../DEPLOY-PATTERN.md`.
- Одна роль БД на сервис и админку оставлена сознательно (разделять на роль миграций и рабочую роль, отложено, см. `TODO.md`).
- Compose или юниты в репозитории злодею почти не помогают (порты на localhost, лимиты, пути к файлам настроек, монтирование сокета), безопасность держится на правах и изоляции, а не на секретности; но по решению владельца серверные файлы всё равно живут вне репозитория.

## Git flow и окружения GitHub (2026-10-25)

- Ветки: `main` (прод, слияние = деплой), `develop` (по умолчанию, фичи ветвятся от неё), `release/<версия>` (подготовка выпуска от `develop`, потом PR в `main` и слияние обратно в `develop`), `hotfix/…` (от `main`). Ветка `release` без косой черты не допускается (конфликт имён git с `release/…`). Владелец явно потребовал `develop` сразу, не «потом».
- Деплой на прод только из `main` (окружение `production`). Из `release/*` позже на стейджинг по кнопке: окружение `staging` создано (ветки `release/*`), secrets и workflow пока нет, «сейчас не делаем, но настроено так, чтобы можно было».
- **Выключатель выкатки на каждое окружение свой**, переменной репозитория: `DEPLOY_PRODUCTION_ENABLED` (создана), позже `DEPLOY_STAGING_ENABLED`. Причина: `if` на уровне задачи не видит переменные окружения GitHub, а проверка внутри шагов происходит уже после входа в окружение (с доступом к его секретам). Прежнее имя `DEPLOY_ENABLED` отменено.
- **Защита веток недоступна** на бесплатном тарифе для приватного репозитория (rulesets и классическая защита, API: 403). Не настроена; решение (GitHub Pro или работа без защиты) отложено.
- Лимиты бесплатного тарифа: около 2000 минут Actions в месяц (около 500 прогонов по 4 минуты), около 500 МБ приватных пакетов GHCR. Образы копятся по одному на деплой: чистить.

## Туннель Cloudflare как служба (2026-10-25)

- `cloudflared` ставится из официального репозитория и запускается **от отдельного пользователя без прав**, токен лежит в `/etc/cloudflared/tunnel.env` (root, 600). Стандартная команда `cloudflared service install <токен>` не используется: она кладёт токен в файл службы, читаемый всеми, и в список процессов, а сервер общий.
- Маршруты туннеля: `fanvue-games.prozorov.site` → `http://localhost:18080`, `admin.fanvue-games.prozorov.site` → `http://localhost:18090` (адрес с протоколом; внутри контура http).
- Старая DNS-запись от прежнего туннеля мешает создать маршрут (ошибка 1033 при статусе Healthy): удалять до создания маршрута.
- Cloudflare Access на имя админки: не сделано, до этого имя админки не открывать.

## Миграции базы (2026-10-25)

- Миграции применяет сервис (API) при старте, под ролью `fanvue_games` (владелец базы), админка схему не меняет. Отдельной роли для миграций пока нет.
- Владелец хочет: при падении миграции остаётся старая версия. По коду и скрипту так и есть (сервис падает при старте, не становится готовым, скрипт останавливает свободный слот, трафик остаётся на старой версии); живой проверкой не подтверждено (учебный сбой в `TODO.md`). Не откатываются миграции, которые уже успели примениться, и новая версия может не пройти проверку по другой причине (так было с админкой в первой выкатке), поэтому миграции обязаны быть обратно совместимыми.
- Отдельный запуск миграций (режим `migrate` у образа сервиса, шаг в `fanvue-deploy` до слотов, вторая роль БД) владелец одобрил как направление и **отложил до после запуска**. Админка не должна быть владельцем миграций: старт обеих частей не упорядочен, а сервис, обслуживающий фанов, должен сам убедиться, что схема готова.

## Документы владельца (2026-10-25)

- Владелец страдает СДВГ: формулировки отказа («не буду», «не стану», «не буду обходить») выводят его из работы. Допустимо «не могу, потому что …». Короткие ответы, один шаг за раз.
- Версии пакетов EF Core в общем проекте задаются явно: без этого админка получала `Relational` 10.0.4 вместо 10.0.12 и падала при построении модели (первая выкатка).
