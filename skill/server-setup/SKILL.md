# Настройка общего сервера

Единственный источник правды: [README.md](../../README.md) и скрипты в корне набора (`install.sh`, `01-base.sh` … `04-caddy.sh`, `verify.sh`). Здесь только то, как агенту вести себя. Не копируй содержимое README сюда: читай его. Этот набор живёт отдельно от репозиториев проектов, потому что сервер общий.

## Что есть

- `install.sh`: запускает шаги `01-base`, `02-podman`, `03-postgres`, `04-caddy` и `verify.sh`. Параметры: `--harden-ssh`, `--only <шаги>`.
- `verify.sh`: только читает, возвращает код 1 при серьёзной проблеме.
- Схема целиком: сервер общий для нескольких проектов; Caddy и PostgreSQL на хосте, приложения в rootless podman службами systemd (Quadlet), образы собирает GitHub Actions и публикует в GHCR, деплой по SSH с ограниченным ключом, секреты в GitHub.

## Правила

1. **На сервер сам не заходи и ничего на него не отправляй**, пока владелец прямо не разрешил это для конкретного действия. По умолчанию ты готовишь и объясняешь, а владелец запускает скрипты сам.
2. **Не отключай вход по паролю и под root (`--harden-ssh`), пока владелец не подтвердил, что вход обычным пользователем по ключу проверен** во второй сессии. Иначе он потеряет доступ.
3. Не ослабляй защиту: не открывай PostgreSQL и админку наружу, не добавляй порты в `ufw` без обсуждения. Админка приложения только локально (туннель или VPN).
4. Скрипты должны оставаться повторяемыми (идемпотентными) и проверять систему перед работой (Ubuntu 24.04+). Не перезаписывай чужие настройки: сервер общий.
5. Никаких секретов в скриптах и репозиториях. Рабочие секреты приложений живут на сервере или в секретах GitHub, как решит владелец.
6. Разбирай только установку ПО, пока не просят следующий шаг. Порядок шагов: раздел «Что дальше» в README.

## Как действовать

- **«Разверни сервер» или «поставь ПО»:** убедись, что пользователь с sudo и ключом есть, дай команду копирования набора и `sudo bash install.sh` из README, попроси прислать вывод `verify.sh`.
- **«Проверь сервер»:** попроси владельца запустить `sudo bash verify.sh` и прислать вывод. Разбери строки `FAIL` и `WARN`.
- **Добавляешь компонент:** новый шаг `NN-имя.sh` по образцу существующих (проверка Ubuntu, `set -euo pipefail`, повторяемость, русские сообщения), добавь его в `install.sh`, `verify.sh` и таблицу в README.
- **Меняешь скрипты:** проверь `bash -n файл` и, если доступно, `shellcheck`. Не запускай их у себя на машине разработки: они меняют систему.
